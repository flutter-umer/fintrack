### What FinTrack Does (Planned)

FinTrack is a **personal finance management mobile application** designed around a premium FinTech aesthetic. The planned feature set includes:

- Track income and expenses
- Visualize spending via charts and dashboards
- Manage monthly budgets by category
- Set and track savings goals
- Provide automated financial insights

**Current reality:** Only the authentication layer and static UI shells exist. No financial data is stored or retrieved anywhere.

## 4. Application Architecture

### Entry Point Flow

```
main() [async]
  │
  ├── WidgetsFlutterBinding.ensureInitialized()
  ├── SystemChrome.setSystemUIOverlayStyle()    ← Transparent status bar
  ├── Firebase.initializeApp()                  ← Reads firebase_options.dart
  └── runApp(FinTrackApp)
          │
          └── MaterialApp(theme: AppTheme.lightTheme, home: _AuthGate)
                  │
                  └── _AuthGate (StatefulWidget)
                          │
                          ├── [Resolving] → SplashScreen (branded)
                          │
                          ├── [User != null] → HomeScreen(user)
                          │
                          └── [User == null] → LoginScreen
```

### Authentication Flow

```
LoginScreen
  ├── Email login → AuthService.signInWithEmail() → HomeScreen
  ├── Google     → AuthService.signInWithGoogle() → HomeScreen
  └── Sign Up    → navigate to SignupScreen
                        ├── Email signup → AuthService.signUpWithEmail() → HomeScreen
                        └── Google       → AuthService.signInWithGoogle() → HomeScreen

HomeScreen
  └── Logout button → AuthService.signOut() → LoginScreen (stack cleared)
```

### Service Layer

- **`AuthService`** — singleton (`AuthService.instance`). Wraps all Firebase Auth and Google Sign-In logic. Returns `AuthResult` (success/failure wrapper). UI screens never import `firebase_auth` directly except `home_screen.dart` (which accepts a `User` parameter).

### Theme Architecture

- All colors defined in `AppColors` (static const, no runtime computation).
- `AppTheme.lightTheme` is a `ThemeData` applied globally via `MaterialApp`.
- No dark theme implemented.

### Navigation / Routing

- Plain `Navigator.push` / `Navigator.pushAndRemoveUntil` — no named routes, no go_router.
- `_AuthGate` handles the initial auth-state-based routing.
- Auth state survives app restarts via Firebase's persisted session.

### State Management

- No state management library. `setState()` used inside `StatefulWidget` screens.
- `LoginScreen` and `SignupScreen` are `StatefulWidget`.
- `SplashScreen` and `HomeScreen` are `StatelessWidget`.
- `_AuthGate` is `StatefulWidget` (listens to `authStateChanges` stream).

```bash
cd android && ./gradlew signingReport  # Linux/macOS
cd android && .\gradlew.bat signingReport  # Windows
```

- **Applied globally** via `GoogleFonts.poppinsTextTheme()` in `AppTheme.lightTheme`
- Weights used: w400, w500, w600, w700, w800
- Size scale: 10px–34px

### Component Styles

| Component | Style |
|---|---|
| **GlassCard** | `BackdropFilter` blur, white gradient fill, 1.2px white border, emerald shadow, `BorderRadius` 24px default |
| **GlassTextField** | `#F0F3F7` fill, 14px radius, `#E2E8F0` border, emerald focus border 1.5px, red border on error |

| **SocialButton** | White fill, 14px radius, `#E2E8F0` border, light shadow |
| **GoogleIcon** | Custom `CustomPainter` rendering — no external image needed |
| **Background blobs** | Circle `Container` with emerald at 6–12% opacity, positioned off-screen edges |

### Design Philosophy

- **Premium FinTech aesthetic**
- Glassmorphism: `BackdropFilter` blur + translucent white gradient layers
- Soft neumorphism: subtle inset shadows, low-contrast borders
- Emerald/teal as the only accent color
- White and near-white backgrounds throughout
- Large rounded corners (14–28px depending on element)
- No hardcoded screen dimensions — uses `double.infinity`, `MediaQuery`, `Expanded`, `Spacer`
- `SafeArea` used on all screens
- `SingleChildScrollView` with `BouncingScrollPhysics` on form screens

## 14. Next Task

### NEXT TASK: Implement Transaction Data Model and Storage Layer

**Why:**
The entire financial data layer of FinTrack does not exist. Before any UI work (dashboard, analytics, budgets) can show real data, a transaction model and a persistence mechanism must be created. This is the foundational dependency for all remaining features.

**Decision required by developer first:**
Choose storage backend:
- **Option A — Firestore (recommended):** Add `cloud_firestore` to pubspec. Data syncs across devices. Requires Firebase Console setup. Transactions stored per-user under `/users/{uid}/transactions/`.
- **Option B — Local (Hive or SQLite):** Offline-only. No cloud sync. Simpler to start.

**Files likely involved:**

lib/

    └── home_screen.dart              ← Modify: replace hardcoded data

**Dependencies:**

- If Hive: `hive_flutter: ^1.x`, `hive: ^2.x`

**Expected result:**
- `Transaction` model exists with fields: `id`, `amount`, `type` (income/expense), `category`, `date`, `note`

## 16. Development Rules

### File Naming

- Screens: `snake_case_screen.dart` (e.g., `transaction_list_screen.dart`)
- Widgets: `snake_case.dart` (e.g., `transaction_card.dart`)
- Services: `snake_case_service.dart` (e.g., `transaction_service.dart`)
- Models: `snake_case_model.dart` (e.g., `transaction_model.dart`)

### Class Naming

- Screens: `PascalCaseScreen` (e.g., `TransactionListScreen`)
- Private screen sub-widgets: `_PascalCase` (e.g., `_LogoBrand`)
- Services: `PascalCaseService` (e.g., `TransactionService`)
- Models: `PascalCase` (e.g., `Transaction`)

### Business Logic vs UI Logic

- **Business / data logic** → `lib/services/`
- **UI state** → inside `StatefulWidget` using `setState()` (no external state package currently)
- **Do not put Firebase calls inside widget `build()` methods**
- **Do not put navigation logic inside service classes**

### Firebase Access

- All Firebase Auth access goes through `AuthService.instance`
- UI screens should not import `firebase_auth` directly (exception: `home_screen.dart` which accepts a `User` parameter — acceptable)
- If Firestore is added, create a dedicated `TransactionService` (or similar) — do not put Firestore calls in screens

### Authentication

- Do not duplicate auth logic. All auth flows use `AuthService`.
- Do not call `FirebaseAuth.instance` directly from screens.
- After any auth action, check `if (!mounted) return;` before calling `setState` or `Navigator`.

### New Dependencies

- Check if functionality can be done without a new package first.
- Add to `pubspec.yaml` with a caret (`^`) version constraint.
- Run `flutter pub get` after adding.
- Run `flutter analyze lib/` after adding and fix any issues before committing.
- Document the new package in §2 of this file.

### Dart/Flutter Conventions

- Use `const` constructors wherever possible.
- Use `super.key` in widget constructors.
- Dispose all `TextEditingController` and `FocusNode` in `dispose()`.
- Use `if (!mounted) return;` after any async gap in `StatefulWidget`.
- Prefer `Expanded` and `Flexible` over hardcoded sizes.
